# Module 06 — Backups & Disaster Recovery

### Brief Overview

Module 6 covers OADP-based backup and disaster recovery for RHOAI. Participants verify the GitOps-pre-provisioned OADP operator, claim a real NooBaa (MCG) object bucket from the cluster's OpenShift Data Foundation, build the Velero credentials Secret and DataProtectionApplication, back up an RHOAI project namespace (Kubernetes resources only), then simulate data loss and restore from the backup — verifying resource counts, pod states, and restored data. Conceptual sections cover the etcd/cluster-backup.sh layer, the RHOAI CRD dependency graph and restore ordering, and current product gaps framed as RFE opportunities.

### Audience and Time

- **Target personas:** OCP platform administrators, MLOps engineers
- **Prerequisites for this module:** Modules 1–5 completed; OADP operator subscription pre-provisioned by the cluster layer; ODF available for the NooBaa bucket
- **Estimated duration:** 45 minutes

### Learning Objectives

- Describe the two-layer backup strategy for OpenShift: etcd snapshots via the control-plane `cluster-backup.sh` script and OADP/Velero for application workloads
- Explain the scope and limitations of OADP (what it backs up and what it does not)
- Configure OADP with a NooBaa (MCG) object bucket as the backup location
- Create an OADP backup of an RHOAI project namespace
- Restore from an OADP backup and verify the integrity of restored resources
- Diagram the RHOAI CRD dependency graph and explain restore ordering concerns
- Identify current product gaps in RHOAI backup/restore and frame them as RFE opportunities

### Detailed Steps

1. Verify the pre-provisioned OADP operator: `oc get csv -n openshift-adp`
2. Claim the backup bucket: apply the ObjectBucketClaim (`oadp-backups`) and poll for its ConfigMap
3. Build the Velero credentials Secret from the OBC access keys (`cloud-credentials`, removed after creation)
4. Apply the DataProtectionApplication — reads BUCKET_NAME/HOST/PORT from the OBC ConfigMap, `insecureSkipTLSVerify` for the NooBaa service CA
5. Back up the project: apply the velero Backup (ttl 720h, `snapshotVolumes: false`) and wait for phase Completed
6. Simulate data loss: delete a test ConfigMap
7. Restore: apply the velero Restore (`existingResourcePolicy: update`) and wait for Completed
8. Verify restored resources: ConfigMap data back, pod states, data-connection labels
9. Read the etcd backup layer, CRD dependency graph, and product gaps sections

### Key Takeaways

- Two-layer strategy: etcd snapshots for cluster state (control-plane script) + OADP/Velero for application workloads.
- OADP backs up Kubernetes resources and (optionally) volumes — the lab backs up resources only (no PVCs with the modelcar).
- Restore ordering matters: the RHOAI CRD dependency graph (DSC/DSCI → operators → components) determines what must exist before restored CRs reconcile.
- Current gaps (no official RHOAA procedure, no dependency-aware restore, no cross-namespace consistency) are framed as RFE opportunities.

### Infrastructure Notes

- The OADP operator subscription is pre-provisioned via GitOps (`automation/gitops/cluster/oadp/`) — the exercise configures the backup location only.
- The NooBaa bucket is claimed from the cluster's OpenShift Data Foundation — no external S3 required (external S3 is discussed conceptually).
- The backup location credentials are generated by the OBC and never committed; in production use External Secrets Operator or Vault.
- S3-for-OADP remains an open question for future environments.
